## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Area-chip padding trims, inline icon gaps, micro offsets in preview overlays |
| sm | 8px | Grid gap, compact board annotations, close text-to-badge spacing |
| md | 16px | Default element spacing, drag status row gaps, compact panel padding |
| lg | 24px | Section padding inside the shell header and board card |
| xl | 32px | Primary shell spacing and desktop layout gaps |
| 2xl | 48px | Major separation between framed regions when new supporting UI appears |
| 3xl | 64px | Reserved page-level spacing; do not consume inside the board itself |

Exceptions: board interaction targets may render below 44px on smaller puzzle sizes because the board cell itself is the canonical target, but any added action chips, badges, or buttons in this phase must keep a 44px minimum height.

Interaction spacing rules:
- Keep preview and placed-rectangle styling inside the existing cell bounds; do not add gutters or overlays that enlarge the board footprint.
- Keep any live area cue within the board card or immediate board header zone; do not push the board downward on every drag frame.
- Preserve the current mobile board-priority behavior by avoiding new always-visible side panels.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#F3EEE4` | Board cells, calm preview fills, primary puzzle surfaces |
| Secondary (30%) | `#D9E0DC` | Clue cells, metadata pills, stable grouped-region tint for placed rectangles |
| Accent (10%) | `#C56D3D` | Active clue emphasis, valid preview edge, release-settle highlight, keyboard/pointer focus ring |
| Destructive | `#B44C3C` | Reserved for Phase 4 destructive controls only; not used for routine invalid drag feedback in Phase 3 |

Accent reserved for: active clue cell, valid preview perimeter, release confirmation settle, explicit focus-visible outlines, and the live area cue only while the preview is valid.

Color behavior rules:
- Invalid previews must not switch to destructive red as the primary language. Use softened low-saturation contrast built from the existing dominant/text/border palette so invalid states read clearly but calmly.
- Placed rectangles must combine a restrained surface tint with edge separation so regions read as grouped areas instead of flat washes or loud puzzle pieces.
- The board background and shell chrome stay visually quieter than the interaction layer; live placement feedback should become the highest-attention state on the board during drag.

## Interaction Contract

### Drag Model

- Rectangle creation starts only from a clue cell.
- Press on a clue arms placement; active drag begins after a small movement threshold.
- Use the same conceptual model across mouse, touch, and pointer input.
- Touch handling may be slightly more forgiving than desktop through drag threshold and release tolerance, but the interaction must still feel like the same system.
- The selected clue must remain inside the preview rectangle at all times; it is an anchor, not a forced corner.

### Preview Behavior

- Preview updates continuously during drag with no debounce visible to the player.
- The preview must show:
  - current rectangle footprint
  - current area value
  - valid or invalid state
- The area cue must stay readable without covering clue numerals or obscuring cell boundaries.
- Valid previews should feel crisp and confident through a cleaner edge and slightly warmer emphasis.
- Invalid previews should feel soft but clear through muted fill and restrained edge treatment.

### Release Behavior

- Releasing a valid preview commits placement immediately.
- A valid commit should use a subtle settle-in motion: quick surface stabilization plus edge lock-in.
- Releasing an invalid preview must not place anything.
- An invalid release should use a restrained snap-back animation that is noticeable but brief.
- This phase does not add remove, undo, reset, completion modal, or progression calls to action.

### Board Composition Rules

- Keep the board as the primary focal point inside the existing shell.
- Do not move puzzle metadata above the board during drag.
- Do not introduce persistent helper panels, legends, or validation logs in Phase 3.
- Any live status copy should be compact and subordinate to the board, not a replacement for visual feedback.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Place Rectangle |
| Empty state heading | No rectangles placed yet |
| Empty state body | Drag from a numbered clue to preview a rectangle. Release when the area matches the clue and the outline turns valid. |
| Error state | Placement unavailable. Reload the puzzle and try again. If the issue persists, restore the bundled starter pack and rules files. |
| Destructive confirmation | None in Phase 3 |

Copy rules:
- Use short instructional copy only when the board has no placements yet or input fails unexpectedly.
- During active drag, prefer terse labels such as `Area 6`, `Valid`, or `Doesn't match clue` over sentence-length coaching.
- Invalid-state labels should name the problem directly and calmly; avoid alarmist wording such as `Error` or `Warning` for routine rule failures.
